# Zalo E2EE Implementation Design for Nexora

**Date:** 2026-10-30  
**Source Spec:** `/media/Data/github.com/Nexoraxx/Client/docs/09-e2ee.html`  
**Target:** Nexora Server (Bun + SQLite) & Nexora Frontend (React + Tauri)  

## 1. Intent & Why
Nexora is an unofficial desktop client for Zalo. Currently, when users communicate in end-to-end encrypted (E2EE) conversations, messages arrive as ciphertext (`chat.e2ee` cmd 551) which Nexora cannot decrypt without local Signal keys and session management. Re-implementing Zalo PC v26.10.20's E2EE protocol enables Nexora to seamlessly send, receive, and display E2EE messages like official Zalo PC.

## 2. Goals & Scope
- **1-1 E2EE Messaging:** Full support for 1-1 encrypted chats (text, quote, sticker, links).
- **Zalo PC Compatibility:** Register as `deviceId 2` (PC platform) and derive identity key using `clamp(SHA-256("${uid}:2"))`.
- **Signal Protocol v3:** Utilize Zalo's modified Signal v3 engine with HKDF tags:
  - Session info: `"ZaloText"`
  - Ratchet info: `"ZaloRatchet"`
  - Message keys info: `"ZaloMessageKeys"`
  - Max message keys: 10,000
- **Key Store:** Implement `SignalProtocolStore` directly on Nexora SQLite tables: `e2ee_identity`, `e2ee_prekey`, `e2ee_signed_prekey`, `e2ee_registration`, `e2ee_session`, `e2ee_deciphered`, `e2ee_metadata`.
- **Signaling via WebSocket RPC:** Manage bundle submission, bundle fetching, and session initialization over WebSocket chat commands (540, 541, 542, 543, 544, 545, 548, 549, 564, 580, 581).
- **HTTP Transport for Sending:** Send encrypted payloads via `POST /api/e2ee/pc/message/*` to the `chat_e2e` service endpoint.
- **WebSocket Transport for Receiving:** Intercept and decrypt cmd 551 (`RECEIVE_ONEONE`) and cmd 535 (`PUSH_MISS`), store plaintext into `message` table with `e2eeStatus = 1`, and broadcast to UI.
- **UI Integration:** Display E2EE lock badge in conversation list and chat header; allow upgrading a conversation to E2EE.

## 3. Non-Goals & Anti-Goals
- **Group E2EE:** Group E2EE is permanently deactivated in Zalo PC v26.10.20 (`DEACTIVATE_E2EE_GROUP = true`). Non-goal.
- **Exposing Private Keys:** Signal private keys must never leave the local Bun server SQLite database; the frontend only receives decrypted text and encryption status flags.
- **Breaking Plaintext Chat:** Plaintext messages (cmd 501 / standard endpoints) must continue working seamlessly.

## 4. Architectural Components

### 4.1. `libsignal` Wrapper (`server/src/third-party/signal/libsignal.ts`)
Loads `pc-dist/libs/libsignal-protocol.static.js` in Bun, providing `KeyHelper`, `SignalProtocolAddress`, `SessionBuilder`, `SessionCipher`, and `Curve`.

### 4.2. `SignalSqliteStore` (`server/src/third-party/signal/signal-store.ts`)
Implements the `SignalProtocolStore` interface:
- Identity: `getIdentityKeyPair()`, `getLocalRegistrationId()`, `saveIdentity()`, `isTrustedIdentity()` (returns `true` per Zalo design).
- PreKeys: `loadPreKey(id)`, `storePreKey(id, keyPair)`, `removePreKey(id)`.
- Signed PreKeys: `loadSignedPreKey(id)`, `storeSignedPreKey(id, keyPair)`, `removeSignedPreKey(id)`.
- Sessions: `loadSession(identifier)`, `storeSession(identifier, record)`.
- Deciphered cache: `getDeciphered(key)`, `saveDeciphered(key, content)` (backed by `e2ee_deciphered`).

### 4.3. `SignalServerManager` (`server/src/third-party/signal/signal-server-manager.ts`)
Handles WebSocket RPC request-response:
- Socket frame: `[1][cmd uint16 LE][0][JSON { cmd, subCmd: 0, data: { reqId, data } }]`
- `getKeyId()`: cmd 564
- `submitBundle(bundle)`: cmd 540
- `submitPreKeys(preKeys)`: cmd 542
- `getBundle(uids)`: cmd 541
- `initSession(uidTo, deviceData)`: cmd 543
- `ackInitSession(uidTo, deviceData)`: cmd 544
- `doneProcessSession(info)`: cmd 545
- Listens for server pushes: cmd 549 (`REQUEST_PREKEYS`), cmd 548 (`NOTIFY_DELETE_KEY`), cmd 580 (`DISABLE`), cmd 581 (`ENABLE`).

### 4.4. `E2eeService` (`server/src/modules/messages/services/e2ee.service.ts`)
Orchestrates:
- Bundle registration on account attach: checks `getKeyId` vs local registrationId. If missing or mismatched, generates bundle and calls `submitBundle`.
- Session establishment: builds session using `getBundle` + `SessionBuilder.processPreKey` + `initSession`.
- Encrypting outgoing message: fans out across recipient's devices and own companion devices. Encrypts fields, constructs payload, posts to `chat_e2e`.
- Decrypting incoming message: parses cmd 551, loads session, decrypts using `SessionCipher`, stores plaintext in SQLite, and emits event.

### 4.5. Message Service & Controller Integration
- `MessageService.send()` checks if target conversation is E2EE. If yes, routes to `E2eeService.sendMessage()`.
- Listener hook for cmd 551 in `ZcaService` delegates to `E2eeService.handleIncomingE2ee()`.
- Restores decrypted messages in conversation history query.

### 4.6. Frontend UI
- Conversation item badge showing E2EE lock icon.
- Header showing E2EE lock and encryption badge.
- Upgrade to E2EE button / action in thread details.

## 5. As built (after final review)
- **Signal stack per account** in `server/src/third-party/signal/`: `signal-store` (SQLite store), `signal-server-manager` (socket RPC in PC's envelope), `e2ee-session-manager` (keys, sessions, handshake, pushes), `e2ee-message-receiver` / `e2ee-message-sender`, wired to the chat socket by the injectable `E2eeService`.
- **Which conversations are encrypted** comes from Zalo's `GET_LIST_USER_E2EE` (563) and the ENABLE/DISABLE pushes (`e2ee_metadata.status`), not from message history. Until the list loads, conversations with E2EE history refuse sends.
- **`message.e2eeStatus`** uses Zalo PC's values: 3000 decrypted, 3001 failed, 3003 encrypted for an older key, 3006 our own send echoed back.
- **Scope shipped:** text (with styles) is sent and received end-to-end encrypted, including decrypting quoted text on received replies. Sending replies, media, stickers, links, GIFs, cards and forwards into an encrypted conversation is refused with a message rather than sent as plaintext. Received non-text E2EE messages stay "Tin nhắn được mã hoá đầu cuối".
- **Not yet:** media E2EE (AES-GCM uploads), E2EE replies/recall/delivered receipts, resend v3, the "upgrade to E2EE" action, an opt-in for taking over the device-2 slot.
